# 셀프 리뷰

PR, 현재 브랜치, 또는 릴리즈 후보의 변경을 검토할 때 사용한다.

```text
$self-review                         # 현재 브랜치의 PR 또는 로컬 변경
$self-review <PR 번호 또는 URL>      # 지정 PR
$self-review --base main             # 릴리즈 후보의 로컬 변경
```

PR 번호나 URL이 있으면 그 PR을 검토한다. 인자가 없으면 현재 브랜치 PR을 찾고, 없으면 `develop` 기준의 로컬 검토로 전환한다. `--base main`은 릴리즈 로컬 검토에만 사용한다. PR 조회 실패만으로 PR을 생성하지 않으며, 가능한 범위에서 로컬 검토를 계속한다.

## 작업 경계

- 저장소 루트와 변경 경로의 `AGENTS.md`, `CLAUDE.md`, `.github/`의 이슈·PR 템플릿을 먼저 읽고 그 규칙을 우선한다.
- 기본 순서는 **리뷰 → 결과 초안 → 게시 승인 → 수정 승인 → 수정·검증 → 완료 게시**다. 문제가 없으면 수정 단계를 생략한다.
- 리뷰 요청은 GitHub 코멘트 게시, PR 생성·Ready 전환·병합, 코드 수정 권한을 주지 않는다. 각 외부 변경 전 대상과 내용을 보여 주고 명시적 승인을 받는다.
- 기존 변경을 보존한다. 시크릿, 개인정보, 전체 환경 변수, 민감 로그는 결과에 복사하지 않는다.
- `✅ 셀프 리뷰 통과`는 셀프 리뷰의 통과 판정이며, 저장소 정책이 허용한다면 팀원 Approve 요건을 대신할 수 있다.

## 1. 검토 대상을 분리한다

저장소 루트에서 상태, 현재 브랜치, 저장소, PR 메타데이터를 확인한다.

```bash
git status --short --branch
git branch --show-current
gh repo view --json nameWithOwner
gh pr view --json number,url,title,body,baseRefName,headRefName,headRefOid,isDraft
```

- 지정 PR이면 이후 `gh pr` 명령마다 그 PR을 명시한다.
- 일반 로컬 검토의 base는 `develop`, 릴리즈 검토의 base는 `main`이다. 실제 PR base가 다르면 이를 보고하고 실제 base로 검토한다.
- PR diff와 로컬 작업물을 섞지 않는다. 로컬 `HEAD`가 `headRefOid`와 다르거나 미커밋 변경이 있으면 각각의 범위와 결론을 분리한다.
- 미추적 파일은 PR diff에 포함되지 않는다. 상태 목록에서 확인하고, 로컬 검토라면 별도 검토한다.
- 커밋만으로 base에서 분기했다고 결론 내리지 않는다. merge-base·그래프·필요 시 reflog로 확인하고 증명할 수 없으면 `확인 필요`로 남긴다.

로컬 diff는 원격 base를 최신화한 뒤 확인한다. fetch가 실패하면 오래된 로컬 ref를 사용했다는 한계를 결과에 적는다.

```bash
git fetch origin <base>
git rev-list --count origin/<base>..HEAD
git diff --stat origin/<base>...HEAD
git diff origin/<base>...HEAD
git log --oneline --graph origin/<base>...HEAD
git merge-base origin/<base> HEAD
git diff --name-only <base>...HEAD
git diff --cached
git diff
```

PR 검토에서는 `gh pr diff <PR번호>`도 확인한다.

## 2. PR 템플릿을 확인한다

PR이 있을 때만 실제 템플릿과 본문을 대조하고, 사용한 템플릿 경로를 기록한다. 기본 템플릿은 `.github/pull_request_template.md`이며 일반 작업 PR의 base는 `develop`이다. `develop → main` 승격 PR에는 저장소의 회의 승인 절차를 추가로 적용한다. HTML 주석, 안내문, 예시, 빈 목록, 남아 있는 플레이스홀더는 작성 내용으로 세지 않는다.

다음을 확인한다.

- 제목의 타입·길이 형식
- 관련 이슈가 있으면 `Closes #번호`로 연결했는지
- 변경 목적·사항이 실제 diff와 일치하는지
- 체크된 검증의 실제 결과, 미실행 사유와 위험
- base에 맞는 템플릿 사용 여부
- 자격증명·비밀 환경 파일 포함 여부
- base와 비교한 브랜치 근거

PR이 없으면 템플릿은 `미확인`으로 둔다.

## 3. 코드와 검증을 검토한다

1. PR·이슈·요청에서 바뀌는 동작과 기대 결과를 한두 문장으로 정리한다. 불명확한 요구와 확인 가능한 범위를 구분한다.
2. 테스트부터 읽어 정상·경계·실패 사례를 파악한다. 테스트 부재나 불충분함은 누락으로 기록하되, 그것만으로 결함이라고 단정하지 않는다.
3. 전체 diff, 변경 파일 전체, 호출부를 읽고 입력부터 검증·권한·상태 변경·저장·응답까지 추적한다. 외부 서비스와 DB의 실패 동작도 확인한다.
4. 변경에 해당하는 관점만 적용한다: 정확성, 테스트, 단순성·구조, 보안·개인정보, 성능, UI·접근성, 데이터 호환성·마이그레이션·롤백.
5. 변경 경로에 맞는 테스트·정적 검사·빌드·수동 확인을 실행한다. 실행하지 못했다면 사유와 위험을 기록하며, CI·로그가 대상 PR 커밋 결과인지 확인한다.
6. 발견 사항은 위치와 실행 경로를 다시 따라 재현 조건, 기대 동작, 실제 영향을 확인한다. 입증하지 못한 사항은 결함이 아니라 `확인 필요`로 분리한다.

저장소 스크립트와 CI를 우선하고, 변경 파일에 가까운 테스트부터 실행한다. 인증·권한·결제·민감정보·외부 연동 변경에는 보안 검토를 포함한다. 성능 개선이 아닌 PR에 프로파일링을 일률적으로 요구하지 않는다.

## 판정 기준

| 심각도 | 기준 | 처리 |
| --- | --- | --- |
| Critical | 보안 침해, 데이터 손실, 핵심 기능 중단 | 진행 전 수정 필요 |
| Important | 재현 가능한 기능 오류·회귀, 요구사항 누락 | 진행 전 수정 필요. 예외는 명시적 승인과 위험 기록 필요 |
| Suggestion | 동작 결함은 아니나 개선 가능 | 선택 제안; 승인 차단 사유 아님 |

결함에는 심각도, 파일·줄, 재현 조건, 기대·실제 영향, 근거, 수정 방향을 쓴다. 같은 원인은 하나로 묶는다.

- 미해결 Critical 또는 Important가 있으면 `❌ 수정 필요`.
- 둘 다 없고 필수 검증·근거가 있으면 `✅ 셀프 리뷰 통과`.
- 대상 SHA, 요구, 검증 근거가 부족하면 `확인 필요`와 필요한 정보를 명시.
- 사용자가 위험을 수용해도 남은 위험과 결정을 기록하며 자동으로 `✅`로 바꾸지 않는다.

## 4. 초안을 먼저 제시한다

외부 게시 전에 다음 형식의 결과 초안을 사용자에게 제공한다.

```text
## 셀프 리뷰 결과 (`$self-review`)

브랜치: <head> → <base> | 커밋: <개수>
검토 대상: <PR 번호·URL 또는 로컬 리뷰>
검토 시점: PR head SHA <sha 또는 해당 없음> | 로컬 HEAD SHA <sha>
미커밋 변경: <포함 여부와 파일 또는 없음>

### 템플릿
- 경로: <실제 템플릿 경로 또는 미확인>
- ✅ / ❌ / 확인 필요: <항목 — 근거>

### 코드 품질
- <심각도, 파일·줄, 재현 조건, 근거, 영향, 수정 방향>
- <발견된 문제가 없으면 검토 한계>

### 검증
- <실행 명령과 결과 또는 미실행 이유·남은 위험>

### 판정
<✅ 셀프 리뷰 통과 / ❌ 수정 필요 / 확인 필요>
```

게시 승인을 받으면 대상 PR과 저장소를 다시 확인한다. 게시 직전 `headRefOid`가 리뷰한 SHA와 다르면 게시하지 말고 diff를 재검토한다. 승인된 본문은 임시 파일에 작성하고 셸 문자열로 직접 삽입하지 않는다.

```bash
gh pr review <PR번호> --repo <owner/repo> --comment --body-file <리뷰본문파일>
```

성공 여부를 확인한다. PR이 없거나 게시 승인이 없으면 초안만 제공한다.

## 5. 승인된 수정만 반영한다

수정 필요 항목마다 현재 상태, 제안 수정, 범위를 보여 주고 명시적으로 승인된 항목만 수정한다. 수정 후 관련 검증과 diff 검토를 다시 실행한다.

- 통과한 변경만 명시적으로 stage하고, 실제 변경을 설명하는 커밋을 만든다. `git add .`는 사용하지 않는다.
- 저장소 규칙과 승인 범위를 따르며, `main`·`develop` 직접 push, force push, 브랜치 삭제는 하지 않는다.
- 검증 실패·미완료 상태에서는 커밋·push하지 않는다.
- 반영 후 수정 항목, 커밋, 검증 결과, 남은 문제를 담은 완료 코멘트 초안을 작성한다. 게시 승인 없이는 초안만 제공한다.

`develop` 대상 PR은 저장소 정책이 이를 허용할 때 `✅ 셀프 리뷰 통과`로 팀원 Approve 요건을 대체할 수 있다. `develop → main`은 저장소의 별도 검토·승인 절차를 따른다.
